## 1. Launch and configuration

The installed entry point is `aisc_salesforce = aisc_salesforce.app:main` (`pyproject.toml`, `[project.scripts]`). The full interactive command is `uv run aisc_salesforce process-profile-updates`. Its default artifact directory is `staged_profile_updates`; `--output-dir` changes it, and `--no-color` changes terminal presentation. The `stage`, `prepare SESSION_ID`, and `review SESSION_ID` subcommands run individual phases. These commands are documented here, not executed. See `app.py:128–179,278–335,711–892`.

Two similarly named commands have different scope. `stage-profile-updates` exports a read-only Salesforce snapshot, without performing review. `profile-updates` runs Case preparation for recent Audits and New submissions; it does not perform the interactive Contact/role/response workflow (`app.py`, `_run_stage_profile_updates:697`, `_run_profile_updates:678`).

The interactive launcher loads `.env` using `setdefault`, so existing environment variables win. It requires nonblank `CERTIFICATION_QUEUE_ID` and `PRIMARY_RESPONDER_ID`, then obtains an OAuth client-credentials token using `SF_CLIENT_ID` and `SF_CLIENT_SECRET`. `SF_LOGIN_URL` optionally specifies an HTTPS org/token endpoint; otherwise the Salesforce production token endpoint is used. The client uses REST API `v60.0` and 30-second requests. Missing configuration and unsuccessful responses raise errors; there is no general automatic retry loop in `_request`. See `app.py`, `_load_dotenv:973`, `get_profile_update_configuration:960`; `salesforce.py:15–19`, `get_credentials:53`, `get_oauth_url:63`, `request_access_token:81`, `_request:449`.

## 2. Capture a session before preparing Cases

Production `ProfileUpdateProcessingWorkflow.run` calls **stage → prepare → review** (`P:456–465`). Alternate injected-writer compatibility paths below this branch use a different setup order; they are not the normal CLI path.

`ProfileUpdateStagingService.stage` initially queries `Company_Profile_Change__c` with `Status__c = New`, ordered by `CreatedDate ASC, Id ASC`. Explicit-ID refreshes query those IDs without a New-status restriction. It reads target Accounts, their parents, siblings and direct children, relevant Contacts, and related Profile Update Cases. No Salesforce writes occur in this staging service (`S:166–295`).

Submissions share a CSV row only when Account ID and normalized submitter email comparison key match. That key ignores dots in the local part for every domain. Missing Account/email gets a record-specific key, preventing accidental blank-value grouping. Within a group, later nonblank values replace earlier ones field by field; a blank does not clear an earlier value. Role details also merge field by field, potentially combining different submissions. Comments and personnel notes are retained in submission order and also stored as individual request items (`S`, `_group_submissions:746`, `_merge_records:763`, `_collect_submitted_values:772`, `_merge_roles:800`, `_build_row:296`).

If any revised address component is supplied, absent components are supplemented from Account billing fields. Staging can also supplement role details from other submitted roles and existing Contacts. These are review context, not proof that a participant requested every displayed value. The interactive Contact collector later uses fresh, explicitly submitted fields (`S`, `_populate_address:548`, `_resolve_role:819`, `_fill_missing_optional_role_fields:1086`; `P`, `_collect_contact_work:2033`).

`publish_staging_session` writes `profile_updates.csv` and `review_queue.json` to a temporary directory, flushes them, then publishes the directory by rename. Session IDs use UTC seconds with numbered collision suffixes. The queue tracks setup, changes, blockers and saved outcomes; it is a local progress record, not a Salesforce transaction (`P:862–924`; `review_queue.py`, `build_review_queue`, `ReviewQueueStore`).

## 3. Prepare Cases, including writes before detailed approval

`prepare` loads the exact session and prepares only captured submissions with Accounts whose Case setup is unfinished. It invokes `ProfileUpdateService.run(submission_ids=...)`; this skips the Audit query and still requires the selected submissions to be New. Case setup failures mark setup failed and stop detailed review. Unresolved submitter identity is reported as manual follow-up but does not itself stop Case creation (`P:534–618`; `C`, `run:184`, `_count_record:262`).

`C._profile_cases` finds Cases on the same Account with `Subject LIKE '%Profile Update%'`, including closed Cases, newest first. `_process_submission:349` applies this order:

1. If a parseable standard subject already contains the submission name, skip ordinary setup. For the newest submission on that Account, a resolved submitter can still replace Case `ContactId`.
2. For other same-name subjects, an exact existing summary in Chatter causes a skip; otherwise post the summary to the newest same-name Case and reuse it.
3. Otherwise reuse the newest received-profile-update Case: append the submission reference to its subject, possibly replace its Contact, then post the summary. This branch does not explicitly reopen a closed Case.
4. Otherwise build the standard received subject. Reuse the newest Case whose subject contains “profile update expected”, applying the full Case payload; if none exists, create a Case. Then post the summary.

The full payload sets `Subject`, `AccountId`, `ContactId`, configured `OwnerId` and `Primary_Responder__c`, `Status = Pending`, portal origin/label for submissions, `Sub_Label__c = Profile Change`, and empty `Description`. Converting an expected Case can therefore replace routing fields and clear Description (`C`, `_case_payload:525`; exact picklist strings in `salesforce_enums.py`). Subject parsing, appending, and length validation live in `profile_update_subjects.py`.

Case Contact selection here is simpler than interactive matching: query Contacts by submitted email, compare trimmed/case-insensitive email, prefer matches on the target Account, and accept only one preferred match. One external match can therefore be selected when no Account match exists. The newest submission per Account supplies this identity, ordered by `(CreatedDate, Id)`; it need not be the oldest submission being processed. Missing identity defers follow-up; expected-Case conversion preserves an existing Contact when no new identity is resolved. Chatter posting checks exact message equality (`C`, `match_contact:122`, `_submission_contact:564`, `_post_if_missing:584`).

The separate `profile-updates` command first handles Audits dated inclusively from today minus 30 days through today, with the profile-form flag true and explanation other than blank/`none`/`n/a` after trimming/casefolding. It reuses an exact expected subject, otherwise reuses a received Case (reopening it Pending if closed), otherwise skips creation if any Profile Update Case was created on/after the Audit date. New Audit Cases use Web/Auditing routing. It posts explanation to the Case and a Case-number reference to the Audit feed, not an Audit field update (`C`, `is_eligible_audit:111`, `_process_audit:274`, `_reconcile_audit_messages:323`). This Audit branch is absent from normal session preparation.

## 4. Resume, repair missing Accounts, and prioritize batches

`ProfileUpdateProcessingWorkflow.review` loads the session and saved queue. A completely finished session with matching completion evidence in `review_audit.jsonl` returns immediately. Missing submission Accounts are repaired now: query New captured submissions with null `Account__c`; use submitted Certification ID or ask for one. One Account match is accepted automatically; multiple matches show a numbered list, default **1**, with **P** to enter another Certification ID. No match repeats the lookup. The chosen Account is immediately written to submission `Account__c` (`P:619–749`, `_choose_submission_account:1526`).

Certification IDs matching the numeric/date/suffix pattern gain a zero-padded variant; suffix `O` also tries `F`, `E`, and `P`. This is a hard-coded equivalence assumption, not an identity check (`P`, `_certification_id_lookup_candidates:6967`).

After repairs, unfinished Case setup runs. The service refreshes the exact captured IDs, verifies that the same set returned, replaces the session CSV and refreshes the queue. It does not add newly arrived submissions (`P:619–749`).

A staged row must match exactly one Account Case containing **all** source submission names. Partial or multiple matches block it (`S`, `_populate_case:476`). `build_case_batches` groups rows by `(AccountId, CaseId)`; missing Account or non-matched Case raises an error. Batches with a Key Data submission strictly older than **seven days** go first, then earliest submission, Account ID and Case ID. The key-update date is submission creation time, not effective date. Exact `Type__c = Key Data` supplies this priority flag (`P:1117–1202`; `S`, `_is_key_update:1189`). Completed queue batches are skipped; non-reviewable blockers leave a batch pending and advance to another (`P`, `review:1623`).

## 5. Show context and run early operator checks

For each batch, `_review_resilient_batch` fetches fresh source submissions, refreshes request items, displays Case/submitter/comment/effective-date/key-answer/warning context, checks Account routing and displays Account History. It saves original role Contact snapshots for later response wording (`P:1810–2032`, `_show_case_context:4903`).

Routing reads one direct child level. A qualifying target Account (`Certified` or `Initials`) is used itself unless qualifying children create a hierarchy conflict. A nonqualifying parent routes to qualifying direct children. No qualifying targets, hierarchy conflict, or differing current child values for requested fields blocks Account/role work and creates handoff context; unrelated Contact work can still occur (`P`, `_ParentRouting.blocked:303`, `_preflight_parent_routing:4654`, `_defer_parent_batch:4818`).

History normally covers each submission's Chicago calendar day. A blank **Key Data** submission uses ±6 hours instead, with overlapping windows merged. For these blank submissions, a change by one hard-coded staff display name selects an acknowledgment; otherwise the script requests clarification. The identity literal is intentionally omitted here to avoid reproducing personal names; it is visible in `_show_account_history:5167–5195`. Any field changed by that name qualifies: this is not proof that the requested update was made. Responses are displayed and the operator must answer yes/no about sending them. Missing email or “no” keeps those sources open and Case pending. This special response is recorded in the audit, not passed to the normal response-text writer (`P`, `_show_account_history:5016–5287`).

Every row then shows submitted, supplemented, and current values, followed by **C/Continue** or **Q/Quit**, default Continue. This happens before this batch's ordinary review writes, but after Case preparation, possible Account repair, and the special history-response prompts. Quit attempts to keep the Case Pending and stops the remaining review. It does not undo setup or prior batches (`P`, `_show_profile_update_overview:4385`, `_checkpoint_row:4345`, `review:1680`). After all checkpoints, the batch Case is written Pending unless saved outcome already says closed (`P:1900–1910`).

## 6. Resolve people, reconcile fields, then save Contact changes

The processor collects fresh submitter and role occurrences, preserving source IDs and roles. A partial role proposal with no email may use its staged/current role Contact ID unless staging classified it as new. A name-only role submission that differs from that incumbent's first or last name suspends this fallback and requires an identity choice before Contact field reconciliation. Exact first-and-last-name matches are searched across the target Account family, and every match is shown. The reviewer can select a match, explicitly rename a generic/shared functional Contact, create a Contact, or defer. Selecting a Contact resolves identity only; Contact fields and the Account role link still receive their own reviews. Deferral leaves the Case Pending and the queued batch recoverable. Title-only and phone-only proposals retain the incumbent fallback. Otherwise occurrences group by email comparison key; unsafe partial proposals with neither valid email nor an existing identity are ignored. Contact searches include exact submitted emails and all family Contacts (target, parent and siblings). The candidate set is not a global fuzzy search (`P`, `_collect_contact_work:2196–2487`, `_review_role_name_identity:3588`).

`contact_resolution.resolve_contact:269` classifies candidates: one family exact normalized email without external ties is existing; otherwise one family dot-insensitive key without external ties is existing. Shared mailboxes, external matches, ties, and name-derived evidence require operator choice. A single same-domain name-pattern candidate one insertion/deletion/substitution or adjacent transposition away becomes “likely typo”. Operator confirmation is required, and the suspected submitted email is excluded from field reconciliation. No safe match becomes a new-Contact proposal. See `contact_resolution.py`, `normalize_email:153`, `is_single_edit_or_transposition:212`, `family_account_ids:240`; `P`, `_review_resolution_choice:3301`.

Ambiguous identity displays candidate details and asks for a number, **create/c**, or **ignore/i**, with no default. Ignoring prevents Contact writes and can later cause a role handoff. Resolving to the same Contact merges work; conflicting submitted field values display their sources and require a numbered value or **current** (`P`, `_resolve_contact_identities:2324`, `_prompt_ambiguous_resolution:3375`, `_reconcile_contact_fields:2365`).

Names/titles use token-based title casing with the explicit exceptions in `contact_normalization.py:10–35` (including executive acronyms and selected special spellings); email is trimmed/lowercased. Recognizable North American phones become `AAA.BBB.CCCC xEXT`; unsupported formats retain their trimmed text. These are formatting rules, not phone validity checks. Field equality itself is exact equality of display strings after trimming; case/format-only differences can be proposed (`contact_normalization.py:53–103`; `P`, `_display:6749`, `_values_equal:6823`). Blank submitted values generally do not clear fields.

For each Contact the operator sees a reconciled comparison, then each changed field gets **A/apply automatically**, **M/make manually**, or **N/will not be made**, with no default. Equal fields are audited no-ops. All Contact decisions are collected before automatic Contact writes; all automatic Contact writes precede manual Contact follow-up (`P:2686–3101`).

Approved changes are saved in at most one request per existing Contact, after a fresh-value conflict check. New Contacts use `AccountId = batch.account_id` plus approved fields and require an automatically approved LastName, unless manual creation is selected. The script then can assign a newly created submitter to Case `ContactId`. A partial new Contact may be created with only the approved fields; an identity classification alone is not creation (`P`, `_execute_automatic_contact_work:2771`, `_assign_created_submitter_if_needed:3209`).

Manual new-Contact work asks for the Salesforce Contact ID and verifies Account and approved/manual values. Existing manual fields are reread and verified. A duplicate-rule create failure offers manual create, manual existing-Contact update, alternate-email Contact, or ignore. Recovery selects by email and records manual verification; its checks differ from the ordinary manual-field path (`P`, `_execute_manual_contact_work:2990`, `_verify_manual_contact_field:3102`, `_recover_duplicate_contact:5589`).

Shared-mailbox name conflicts cause handoff. An email-only proposal on an existing shared mailbox can instead propose a company/purpose name while retaining the mailbox: this branch replaces `write_values` with the name changes. Before renaming, all Account-role references must be readable and within the family; external links or read failure cause handoff (`P:2383–2649`).

## 7. Review Account changes, then role links

All current `ACCOUNT_PROPOSALS` fields—Name, Company_Owner__c and the six Billing address fields—are classified operator-only. Changed values are refreshed and handed off, rather than passed to the generic automatic/manual field writer. Already-current values are no-ops. The generic write helper exists, but does not prove these fields are automatically written by the current batch path (`P:118–163`, `_review_account_proposals:5288`, `_operator_only_account_field:6887`).

Future company-name/address changes use Chicago's date and a valid future effective date. The operator must confirm a Case-linked Notion task exists; “no” interrupts review. Python neither creates nor checks that task. It asks whether temporary `f.k.a.` or `(pending address change)` notation was used and displays cleanup instructions. Future-plan delivery is confirmed at finalization. A combined move with company-name or Certification/Principal changes requires closer review and keeps the Case pending (`P:5432–5540`, `_future_effective_date:6924`, `_is_combined_move_review:6936`). Key answers about personnel, QMS, equipment and software are displayed as context; this path does not convert them into direct Salesforce field updates (`S:45–58,572`; `P`, `_show_case_context`).

Role links run after Contact and Account review, using the preserved source mapping and latest applicable submitted role occurrence. The five mappings are:

| Submitted role | Account lookup |
| --- | --- |
| Certification | `Cert_Certification_Contact__c` |
| Principal | `Cert_Principal_Contact__c` |
| Accounting | `Cert_Accounting_Contact__c` |
| Quality | `Cert_Marketing_Contact__c` |
| New York | `Cert_Safety_Contact__c` |

These unusual Quality/Marketing and New York/Safety mappings are explicit in `account_roles.py:53–112`. Role assignment does not mutate Contact fields. Unresolved/ignored Contacts cause handoff. Before replacement, the script searches all five role lookups across Accounts for the former Contact. A submitted role replacement can proceed even when the former Contact holds another role; only the submitted lookup is changed, and the other role lookups stay unchanged. The lookup gets its own A/M/N decision, fresh conflict check, and immediate one-field write or manual verification. A confirmed replacement creates a legacy `Note` on the former Contact, deduplicated by title/body; Note failure causes handoff after the role may already have changed. Former Contacts are not deleted (`P`, `_assign_reconciled_roles:3524`, `_ensure_departure_note:3714`, `_review_proposal:5864`, `_execute_proposal:5944`).

## 8. Requests, response text, Portal Users, and closure—in that order

`_finish_batch:3780` first shows management handoff context if needed. This records local reasons and displays completed versus outstanding work; it does not send a manager message or automatically reassign the Case. Each comment/personnel-note request then requires **addressed** or **handed_off** and a nonblank written result. Handed-off requests keep Case pending. Outcomes are saved to the queue/audit (`P`, `_show_manager_handoff_summary:3922`, `_review_request_items:4110`, `_record_handoff:6369`).

`format_response_emails` produces text grouped by submitter email from successful Account results, role snapshots and request results. It omits rejected/no-op generic proposals; roles can explicitly say “no change”. Duplicate lines are suppressed. The text includes replacements and a standard statement about a separate Portal login email, but Python here does not send that email. Standalone Contact changes are not passed as generic results to this formatter. Text is appended to `response_emails.txt` (duplicate Case/email/text blocks are suppressed), displayed, then the operator answers **yes/no** whether each email was sent. A saved “sent” outcome avoids asking again. These are operator attestations, not delivery checks (`P`, `_ResponseWriter:1269`, `_finish_batch:3794–3863`, `format_response_emails:6554`).

Portal provisioning runs next when there are no blank-response-pending sources and a provisioning service was supplied—even if ordinary response emails were not sent. It considers reconciled Contact IDs, including existing ones. It plans required Profiles from qualifying roles; New York, multiple distinct roles, or a qualifying multi-account family selects RAS. Single-role mappings select Participant, Principal, AP or QC. Profile configuration requires five environment IDs to equal the hard-coded IDs and names in `user_sync_config.py:12–58` (`required_profile_rules.py`, `determine_required_profile:47`; `user_reconciliation.py`, `plan:422`).

The provisioning service reuses an active linked User without applying proposed User field/Profile changes. For a missing User it requires valid Contact identity/email, a supported Certified role, an Account with an active internal owner with a role, correct external Profile license, no username collision, and available license capacity. Initials-only access is deferred with an Enter acknowledgment. `EXTERNAL_USER_LICENSE_NAME` is required; optional `EXTERNAL_USER_ROLE_ID` is added. An optional Account eligibility policy exists but the interactive caller does not supply one. Unreadable license capacity becomes a warning and creation is attempted (`participant_user_provisioning.py`, `provision:136`, `_validate_external_requirements:245`, `_validate_license_capacity:368`).

A new User gets `ContactId`, names, normalized email/username, ProfileId, Alias, timezone/localization and `IsActive = True`; optional role is added. Alias uses first five normalized last-name characters + first first-name character + two-digit year, limited to eight characters. Timezone maps mailing state/province, otherwise Chicago; locale/language are `en_US`, encoding `UTF-8`. Community nickname is optional and not requested by this caller. There is **no existing User update, deactivation or delete** in this workflow (`user_reconciliation.py`, `_desired_user:602`; `user_field_policies.py`, `alias`, `time_zone`, `fixed_localization_fields`; `participant_user_provisioning.py:218–243`).

Provisioning exceptions are caught by `_provision_missing_participant_users:4208`, audited and handed off; the helper returns. Its docstring says raising preserves New sources, but this catch-and-return behavior means finalization can continue to close eligible sources. This is an **observation requiring verification**, not an established external outcome.

Each source is then closed separately with `Status__c = Closed`, unless its blank-submission response is pending or a request has no outcome. Ordinary “email not sent” does **not** prevent source closure. Finally Case `Status` becomes Pending if handoffs/pending flags exist or responses are incomplete; otherwise Closed. A future change may close once task and participant plan are confirmed despite deferred field work. Missing email on successful work or role response also prevents Case closure (`P`, `_finish_batch:3860–3921`).

The next batch is processed automatically. Errors stop review and usually attempt a Pending Case write; failure of that write is also audited. Interrupts preserve earlier writes. The CLI prints session, audit, response and queue paths and batch counts; “completed batches” counts reviewed batches, including ones left pending (`P`, `review:1623–1731`, `_keep_case_pending:6300`; `app.py:751–766,848–862`).

## Observations requiring verification

- Case setup email matching and interactive family matching use different rules; setup can assign a sole external match that interactive review later treats as ambiguous (`C.match_contact`; `contact_resolution.resolve_contact`).
- Subjects and exact Chatter text act as identity/deduplication keys. A standard-subject skip does not repair a missing summary. Subject formatting and independently edited text can affect reuse (`C._process_submission`; `profile_update_subjects.py`).
- Group merging can synthesize values from different dates/people. Dots are ignored for all email domains, although Python does not establish that those addresses identify the same mailbox (`S._merge_records`; `contact_resolution.normalize_email`).
- All company fields are operator-only despite generic automatic Account-update machinery. Key-answer text does not establish that any related business follow-up occurred (`P._review_account_proposals`, `_operator_only_account_field`).
- Shared-mailbox email-only handling replaces the write dictionary with name fields; other proposed changes can be decided but excluded from that automatic payload (`P._reconcile_contact_fields`).
- Duplicate recovery's manual-verification label establishes email-based selection, not the same field-by-field validation used in normal manual creation (`P._recover_duplicate_contact`).
- Blank-history evidence relies on one staff display name, any field change and a ±6-hour window; task creation and email sending are only confirmed verbally (`P._show_account_history`, `_confirm_future_change_task`, `_finish_batch`).
- Provisioning's catch-and-return behavior differs from its preserve-New-source docstring. It can leave the Case Pending while source closure continues. Existing active Users are reused without applying changed Profile/contact-derived values (`P._provision_missing_participant_users`; `participant_user_provisioning.provision`).
- Ordinary unsent responses can coexist with Closed submissions. A failed final Case close happens after source closure; a new New-only staging run may omit those sources. Resuming the exact session and starting a fresh session are materially different (`P._finish_batch`, `ProfileUpdateProcessingWorkflow.review`; `S.stage`).
- No rollback is provided. Local audit/queue publication can fail after an external write; API timeout can leave uncertainty about whether Salesforce committed. Static inspection cannot establish server-side automation or guarantee recovery (`P._update_record:1417`, `_append_audit:6413`; `salesforce.py._request`).

For learning, follow one `ChangeProposal` through preview, decision, API request and `ActionResult`. This shows why a proposed value, an approved value and a saved value are three different things.
